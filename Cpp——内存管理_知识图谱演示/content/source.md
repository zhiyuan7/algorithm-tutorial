## 一、数据类型与地址

### 1. C 和 C++ 中的基本数据类型

在继续讨论内存的分配和生命周期之前，先看看 C/C++ 可以直接保存哪些基本数据。

整数类型包括：

```cpp
char
short
int
long
long long
```

还可以使用 `signed` 和 `unsigned` 指定有符号或无符号整数，例如：

```cpp
unsigned int age = 20;
long long population = 8000000000LL;
```

浮点类型主要包括：

```cpp
float
double
long double
```

例如：

```cpp
double pi = 3.1415926535;
```

C++ 还提供布尔类型 `bool`；C 从 C99 开始提供 `_Bool`，并可通过 `#include <stdbool.h>` 使用 `bool` 这个名字。

### 2. 变量名与地址

一个程序要处理一个整数：

```cpp
int x = 10;
```

从 C/C++ 语言的视角看，我们定义了一个名叫 `x` 的对象，它的值是 `10`。

但从计算机硬件的角度看，事情最终一定会落实为：

> **在内存中的某个位置保存若干个二进制位。**

假设某台机器上 `int` 占 4 字节，并且 `x` 恰好位于：

```text
0x1000
```

那么可以粗略理解成：

```text
地址            内容

0x1000  ┐
0x1001  │
0x1002  │  x = 10
0x1003  ┘
```

CPU 想读取 `x`，最终必须访问对应的内存地址。

因此，从底层看：

\[
\boxed{\text{访问数据，本质上就是访问某段地址对应的内存}}
\]

只不过平时写：

```cpp
x = 20;
```

时，程序员并不需要自己写：

```text
访问地址 0x1000
```

编译器已经替我们完成了从名字 `x` 到具体地址的转换。

这也是为什么普通变量看起来似乎“没有地址”。

实际上：

```cpp
int x = 10;
std::cout << &x;
```

仍然可以取得 `x` 的地址。

所以变量名可以理解成程序员使用的一种高级抽象，而底层真正执行访问时，仍然离不开地址。

### 3. 数组：连续存放多个同类型对象

如果需要存储很多相同类型的数据，可以使用数组：

```cpp
int score[5] = {90, 85, 92, 88, 95};
```

可以粗略想象为：

```text
score[0]  score[1]  score[2]  score[3]  score[4]

  90         85        92         88        95
   │          │         │          │         │
0x1000     0x1004    0x1008     0x100C    0x1010
```

数组最重要的特点之一就是：

> **数组元素在内存中连续排列。**

数组名 `score` 在大多数表达式中会转换为首元素的地址，即 `&score[0]`；这就是数组的起始地址。若已知起始地址以及每个元素 `T` 的大小，就可以找到任何一个元素：

\[
\operatorname{address}(a_i)
=
\operatorname{address}(a_0)
+
i\cdot sizeof(T).
\]

这也解释了为什么数组和指针之间存在非常紧密的关系。

### 4. 结构体：把多个相关数据组织成一个整体

很多时候，我们需要表示的对象不是一个单独的数字。例如学生可能包含姓名、年龄和成绩，于是可以定义结构体：

```cpp
struct Student
{
    char name[20];
    int age;
    double score;
};
```

然后：

```cpp
Student alice = {"Alice", 20, 92.5};
```

`alice` 整体就是一个对象，在内存中拥有一块能够容纳所有成员的空间：

```text
Student alice

┌──────────────────────┐
│ name[20]             │
├──────────────────────┤
│ age                  │
├──────────────────────┤
│ padding（可能存在）  │
├──────────────────────┤
│ score                │
└──────────────────────┘
```

这里的 `padding`（填充字节）是编译器为了让成员从满足其**对齐要求**的地址开始而自动插入的空白字节。许多机器访问未对齐的 `int`、`double` 会更慢，某些平台甚至不允许这种访问；因此编译器通常会让 `int` 的地址是 4 的倍数、让 `double` 的地址是 8 的倍数（具体要求由平台和编译器决定）。

例如在一种常见布局中，`name` 占前 20 字节，`age` 紧接着占 4 字节；此时偏移量为 24，而 `double score` 需要从 8 的倍数地址开始，所以不必额外填充。若成员排列为 `char tag; double score;`，则 `tag` 后通常要插入 7 个填充字节，才能让 `score` 从偏移量 8 开始。结构体末尾也可能补齐，使得结构体数组中的每个元素都满足相同的对齐要求。因此 `sizeof(Student)` 不一定简单等于各成员大小之和。

在通信协议、文件格式或与硬件寄存器交互时，往往需要精确控制字节布局，不希望编译器插入 padding。许多编译器支持用 `#pragma pack` 指定 1 字节对齐：

```cpp
#include <cstdint>

#pragma pack(push, 1)
struct PacketHeader
{
    std::uint8_t type;
    std::uint32_t length;
};
#pragma pack(pop)

static_assert(sizeof(PacketHeader) == 5);
```

这里 `PacketHeader` 的大小为 5 字节：1 字节的 `type` 加 4 字节的 `length`，中间没有 padding。GCC 和 Clang 也常支持 `__attribute__((packed))`。

网络通信通常要确定好包的大小 ，在这个时候取消padding就格外重要了。

## 二、为什么不把所有内存都动态分配？

既然所有数据最终都存储在内存中，那么一种非常自然的想法就是：

> 每当程序运行到需要某个数据的时候，再临时申请一块内存；什么时候不用了，再把它释放掉。

这种方式确实具有极高的自由度。

例如用户输入：

```text
1000000
```

程序才决定申请能够存储一百万个整数的空间。

但是，如果**所有变量都采用这种方式管理**，效率反而会比较低。

原因主要有两个。

### 1. 很多对象的大小和生命周期其实早就知道了

例如：

```cpp
void f()
{
    int x;
    double y;
    int a[100];
}
```

编译器在编译程序的时候就已经知道：

```text
x     → sizeof(int)
y     → sizeof(double)
a     → 100 × sizeof(int)
```

并且它也知道这些对象只在 `f()` 执行期间存在。

既然这些信息提前就知道，就没有必要在运行过程中每次都调用复杂的内存分配器：

```text
寻找空闲空间
→ 登记这块空间
→ 返回地址
→ 使用
→ 再通知内存分配器释放
```

我们完全可以提前规划好这些对象需要的空间。

### 2. 很多对象的生命周期由作用域自动管理

例如：

```cpp
void calculate()
{
    int temp = 100;

    // 使用 temp
}
```

`temp` 的生命周期与它所在的代码块（作用域）紧密相关：执行到它的声明时它被创建，离开 `calculate()` 的函数体时它的生命周期自动结束。函数结束后，程序已经无法再通过变量名 `temp` 访问它，因此也不需要继续保留它。

对于这类自动对象，程序员不必像管理动态内存那样手动决定“什么时候释放”；离开作用域时，编译器生成的代码会自动完成相应的清理工作。对于具有析构函数的 C++ 对象，这还意味着析构函数会在离开作用域时自动执行。

于是，一个自然的问题出现了：

> 能不能根据不同数据的生命周期，采用不同的内存管理方式？

答案就是 C/C++ 中非常重要的几个概念：

\[
\boxed{
\text{静态存储期}
\qquad
\text{自动存储期}
\qquad
\text{动态存储期}
}
\]

它们在典型实现中又经常分别和：

```text
静态存储区
栈
堆
```

联系起来。

## 三、静态存储

### 1. 作用域与生命周期的辨析

这两个概念经常被混淆，但它们回答的是不同的问题：

\[
\boxed{\text{作用域} \neq \text{生命周期}.}
\]

**作用域**描述的是：在哪些代码位置可以通过一个名字访问对象。**生命周期**描述的是：对象从何时创建，到何时销毁并不再存在。

例如下面的 `count`：

```cpp
void f()
{
    static int count = 0;
    count++;
}
```

它的名字只在函数 `f` 的作用域内可见，但对象从第一次执行到声明时创建，一直存在到程序结束。因此它具有局部作用域，却具有静态存储期。

### 2. 静态存储

具有静态存储期的对象在程序运行期间一直存在。它们在程序启动时或第一次执行到相应声明时完成初始化，并在程序结束时才销毁。静态存储期既可能与全局作用域结合，也可能与局部作用域结合。

#### 2.1 全局作用域的静态存储

例如：

```cpp
int global_counter = 0;

double constants[3] = {
    3.14,
    2.718,
    1.414
};

struct Config
{
    int width;
    int height;
};

Config config = {1920, 1080};
```

这些对象在 `main()` 开始前就已经完成相应的初始化，并一直存在到程序结束。在典型操作系统中，它们通常位于程序的数据段等静态数据区域，可以粗略理解为：

```text
程序地址空间

┌──────────────────┐
│ 代码             │
├──────────────────┤
│ 全局/静态数据    │
│ global_counter   │
│ constants        │
│ config           │
├──────────────────┤
│ ...              │
└──────────────────┘
```

#### 2.2 局部作用域的静态存储

局部 `static` 对象只能够在其所在的函数或代码块中通过名字访问，但它不会在每次进入作用域时重新创建：

```cpp
#include <iostream>

void f()
{
    static int count = 0;
    count++;
    std::cout << count << '\n';
}

int main()
{
    f();
    f();
    f();
}
```

输出为：

```text
1
2
3
```

作为对照，普通局部变量 `int count = 0;` 会在每次调用 `f()` 时重新创建，并在函数返回时销毁，因此连续三次调用都会输出 `1`。而 `static int count = 0;` 在第一次执行到声明时初始化一次，后续调用复用同一个对象，所以它的值依次从 `0` 变为 `1`、`2`、`3`。

## 四、自动存储

### 1. 自动存储期：函数中的普通局部变量

再来看最常见的一类对象：

```cpp
void f()
{
    int x = 10;
    double y = 3.14;
}
```

`x` 和 `y` 具有**自动存储期**。

通常情况下，它们被存储在程序的：

\[
\boxed{\text{栈 Stack}}
\]

中。

当程序进入相应的代码块以后，这些对象开始存在；离开代码块以后，这些对象的生命周期结束。

例如：

```cpp
void f()
{
    int a = 10;

    {
        int b = 20;
    }

    int c = 30;
}
```

可以粗略理解成：

```text
进入 f

创建 a

进入内部代码块
创建 b

离开内部代码块
销毁 b

创建 c

离开 f
销毁 c
销毁 a
```

### 2. 栈上的内存分配为什么快？

假设函数：

```cpp
void f()
{
    int x;
    int y;
    double z;
}
```

编译器通常在编译阶段就知道这个函数需要多少局部空间。

假设：

```text
x     4 B
y     4 B
z     8 B
```

那么粗略地说，需要：

```text
16 B
```

执行函数时，不需要复杂地寻找三个独立的空闲区域。

程序只需要移动一下所谓的**栈指针**：

```text
原来：

────────────── ← SP

进入函数：

x
y
z
────────────── ← 新 SP
```

函数返回时，再把栈指针移动回来。

这里的“栈”不仅是存放局部对象的常见区域，也是一个**后进先出**（Last In, First Out，LIFO）的数据结构：最后进入栈的内容，必须最先离开栈。函数调用的嵌套恰好符合这一规则：`f()` 调用 `g()` 时，`g()` 的栈帧压在 `f()` 的栈帧上方；`g()` 返回时，它的栈帧先弹出，随后才轮到 `f()` 返回。

因此嵌套调用中局部对象的生命周期也呈现相同规律：

```text
main() 开始，创建 main 的局部对象
    ↓
f() 被调用，创建 f 的局部对象
    ↓
g() 被调用，创建 g 的局部对象
    ↓
g() 返回，销毁 g 的局部对象
    ↓
f() 返回，销毁 f 的局部对象
    ↓
main() 返回，销毁 main 的局部对象
```

也就是后创建的自动对象会先结束生命周期；这正是栈的 LIFO 规则在函数调用中的体现。

因此，进入函数或代码块时，只需把栈顶向一个方向移动以预留空间；离开时，再把栈顶移回原处即可。既不需要逐块搜索空闲内存，也不需要单独记录每个局部对象的位置。

因此：

\[
\boxed{\text{栈分配通常只是调整一个指针}}
\]

这使得自动对象的创建和释放通常非常高效。

## 五、动态存储

### 1. 动态存储的必要性

动态存储提供两种自动对象难以提供的自由度。

第一，**分配多少内存可以在运行时决定**。例如用户输入后才知道需要保存多少张图片：

```cpp
std::size_t count;
std::cin >> count;

Image* images = new Image[count];
```

在编写程序时，`count` 的值可能是 10、10000 或 50000，因此无法把数组大小预先固定在函数的自动存储中。

第二，**何时创建、何时释放可以由程序自行决定**。动态对象并不在离开某个作用域时自动消失：

```cpp
int* p = new int(42);  // 此时申请并创建对象

// 对象可跨越当前代码块继续使用

delete p;              // 此时才释放并销毁对象
```

所以动态存储的核心是：内存大小与对象生命周期都可以在运行时按需要决定。这种自由度很高；相应地，程序也必须正确负责释放资源，后文会讨论由此带来的风险与改进方式。

### 2. 堆、地址与指针

动态对象的创建、释放顺序和大小都可能不规则，不能像自动对象那样依靠栈的后进先出规则管理。因此它们通常由能够管理不规则空闲块的区域——**堆**（Heap）——管理。

我们可能：

```cpp
A* a = new A;
B* b = new B;
C* c = new C;

delete b;

D* d = new D;

delete a;
delete d;
delete c;
```

创建和释放顺序毫无规律。

对象大小也可能不同：

```text
20 B
300 B
10 KB
2 MB
...
```

因此没有办法像栈一样简单地不断压入和弹出。

我们需要一个能够管理大量不规则空闲空间的内存区域。

这就是通常所说的：

\[
\boxed{\text{堆 Heap}}
\]

可以粗略想象成：

```text
Heap

┌───────────┐
│ 已使用    │
├───────────┤
│ 空闲      │
├───────────┤
│ 已使用    │
├───────────┤
│ 空闲      │
├───────────┤
│ 已使用    │
└───────────┘
```

内存分配器需要维护：

```text
哪些地方空闲？
哪些地方已经使用？
哪一块能够容纳这次申请？
释放以后怎样重新利用？
```

所以堆分配通常比栈分配复杂得多。

**为什么需要指针？**

假设：

```cpp
int x = 10;
```

编译器知道 `x` 是谁，可以自动把：

```text
x
```

对应到某个地址。

但是：

```cpp
int* p = new int;
```

情况不同。

`new int` 到底得到哪块内存，是程序运行时才知道的。

例如这次得到：

```text
0x7A1200
```

下一次可能得到：

```text
0x93FF20
```

于是程序必须把这个运行时产生的地址保存下来。

所以：

```cpp
int* p
```

的作用就是：

> **保存动态申请得到的那块内存的地址。**

例如：

```text
栈

p = 0x7A1200
│
│
│
▼

堆

0x7A1200
┌──────────┐
│   42     │
└──────────┘
```

代码：

```cpp
int* p = new int;

*p = 42;
```

其中：

```cpp
p
```

保存地址。

而：

```cpp
*p
```

表示：

> 找到 `p` 中保存的地址，再访问那个地址上的对象。

**指针本身的存储位置。**

有时我们会简单地说：

> “动态对象在堆上，而指向它的指针在栈上。”

这个说法对很多局部变量场景成立：

```cpp
void f()
{
    int* p = new int;
}
```

这里：

```text
p       通常在栈上
*p      通常在堆上
```

但是这并不是普遍规律。

例如：

```cpp
int* global_p = nullptr;
```

`global_p` 本身具有静态存储期。

再比如：

```cpp
struct Node
{
    Node* next;
};
```

如果：

```cpp
Node* p = new Node;
```

那么：

```cpp
p->next
```

这个指针本身就是动态对象 `Node` 的一部分，因而通常也位于堆中。

因此更准确地说：

> **动态申请得到的是一块内存，而我们必须在某个地方保存它的地址。这个地址通常由一个指针保存，但这个指针自己可以具有静态、自动甚至动态存储期。**

## 六、C：malloc/free 管理动态内存

### 1. malloc 与 free

C 提供：

```c
malloc
```

进行动态内存分配。

例如：

```c
#include <stdlib.h>

int* p = malloc(sizeof(int));
```

`malloc` 的函数接口可以粗略理解成：

```c
void* malloc(size_t size);
```

意思是：

> 请给我一块至少有 `size` 个字节的内存。

例如：

```c
malloc(100);
```

表示申请 100 字节。

成功时它返回：

```c
void*
```

也就是：

> **一块尚未赋予具体类型含义的内存的起始地址。**

因此：

```c
void* raw = malloc(sizeof(int));
```

得到的是一个“通用地址”。

在 C 中可以直接：

```c
int* p = malloc(sizeof(int));
```

因为 `void*` 可以隐式转换成其他对象指针类型。

随后：

```c
*p = 42;
```

最后：

```c
free(p);
```

释放空间。

完整例子：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int* p = malloc(sizeof(int));

    if (p == NULL)
    {
        return 1;
    }

    *p = 42;

    printf("%d\n", *p);

    free(p);

    return 0;
}
```

### 2. malloc 为什么返回 void*？

`malloc` 做的事情只是：

> **申请若干字节。**

例如：

```c
malloc(100);
```

这 100 个字节到底准备存：

```text
25 个 int

12 个 double 左右

一个结构体

字符数组

其他数据
```

`malloc` 本身并不知道。

所以它返回：

```c
void*
```

意思可以理解成：

> “这是一个地址，但我暂时不规定你打算把这里的内容看成什么类型。”

例如：

```c
struct Student
{
    int age;
    double score;
};

struct Student* s =
    malloc(sizeof(struct Student));
```

此时由程序员告诉编译器：

> 我打算把这块内存作为 `struct Student` 使用。

### 3. 申请数组

如果用户输入数组长度：

```c
int n;
scanf("%d", &n);
```

便可以：

```c
int* a = malloc(n * sizeof(int));
```

假设：

```text
n = 1000
sizeof(int) = 4
```

则申请：

```text
4000 字节
```

之后：

```c
a[0] = 10;
a[1] = 20;
```

使用完：

```c
free(a);
```

这就是动态内存特别重要的应用：

\[
\boxed{\text{运行时才能确定数据规模}}
\]

## 七、C++：new/delete 与对象的创建

### 1. 从 malloc/free 到 new/delete

C++ 当然仍然可以调用：

```cpp
malloc
free
```

但 C++ 又提供了：

```cpp
new
delete
```

例如：

```cpp
int* p = new int(42);

std::cout << *p;

delete p;
```

数组则可以：

```cpp
int* a = new int[100];

delete[] a;
```

### 2. new 相比 malloc 多做了什么？

对于：

```cpp
int
double
```

之类的简单类型，两者看起来区别似乎不大。

但考虑一个 C++ 类：

```cpp
class Robot
{
public:
    Robot()
    {
        std::cout << "Robot created\n";
    }

    ~Robot()
    {
        std::cout << "Robot destroyed\n";
    }
};
```

如果：

```cpp
Robot* p = new Robot;
```

`new` 大致完成两个逻辑步骤：

```text
申请足够的内存
        ↓
在这块内存中构造 Robot 对象
```

而：

```cpp
delete p;
```

则大致对应：

```text
调用 Robot 的析构函数
        ↓
释放内存
```

因此：

\[
\boxed{
new \neq 单纯的“申请若干字节”
}
\]

它处理的是：

> **C++ 对象的创建。**

而 `malloc` 主要处理的是：

> **原始字节空间的申请。**

### 3. malloc 与 new 的概念区别

可以把它们粗略理解成：

```text
malloc

“请给我 100 个字节”
```

而：

```text
new Robot
```

更加接近：

```text
“请创建一个 Robot 对象”
```

因此：

```cpp
Robot* robot = new Robot;
```

直接返回：

```cpp
Robot*
```

而不是：

```cpp
void*
```

同时还会执行构造函数。

## 八、内存泄漏与手动释放的风险

无论使用 C 的 `malloc/free` 还是 C++ 的 `new/delete`，只要申请的动态内存没有被正确释放，就会发生**内存泄漏**：对象不再能被程序访问，但对应内存仍处于占用状态。长时间运行的程序若反复发生这种情况，内存占用会不断增长。

虽然：

```cpp
new
delete
```

比：

```cpp
malloc
free
```

更加符合 C++ 的对象模型，但程序员仍然必须记住：

```cpp
new
```

最终要匹配：

```cpp
delete
```

例如：

```cpp
void process()
{
    Robot* robot = new Robot;

    if (something_wrong())
    {
        return;
    }

    delete robot;
}
```

如果：

```cpp
something_wrong()
```

为真，函数直接：

```cpp
return
```

那么：

```cpp
delete robot;
```

根本没有执行。

于是又发生内存泄漏。

更麻烦的是，真实程序还有：

```text
异常
多个 return
多个对象
复杂控制流
对象所有权转移
```

因此“只要记得 delete”在大型程序中并不是一个可靠的工程方法。

C++ 后来采用了一种非常重要的思想：

\[
\boxed{\text{RAII}}
\]

即：

> **Resource Acquisition Is Initialization**

让资源的生命周期绑定到对象的生命周期。

智能指针就是这种思想的重要体现。

## 九、智能指针

### 1. unique_ptr

最常用的智能指针之一是：

```cpp
std::unique_ptr
```

例如：

```cpp
#include <memory>

int main()
{
    std::unique_ptr<int> p =
        std::make_unique<int>(42);
}
```

甚至通常写成：

```cpp
auto p = std::make_unique<int>(42);
```

现在：

```cpp
*p
```

仍然可以访问动态对象：

```cpp
std::cout << *p;
```

但我们不需要写：

```cpp
delete p;
```

当：

```cpp
p
```

离开作用域时，其析构函数会自动释放它管理的动态对象。

即：

```text
进入作用域

p 被创建
↓
动态创建 int

使用 int

离开作用域
↓
p 被自动析构
↓
动态 int 被自动释放
```

这使得资源管理又重新具有类似自动变量的安全性。

因为它表示：

\[
\boxed{\text{唯一所有权}}
\]

也就是说，一个动态对象只能由一个：

```cpp
unique_ptr
```

负责管理。

例如：

```cpp
auto p1 = std::make_unique<int>(42);
```

不能直接：

```cpp
auto p2 = p1;
```

因为这会产生：

```text
p1 ──┐
     ├──→ 同一个对象
p2 ──┘
```

那么到底由谁负责销毁？

为避免这个问题，`unique_ptr` 禁止复制。

但可以转移所有权：

```cpp
auto p2 = std::move(p1);
```

于是：

```text
原来：

p1 ───→ object

后来：

p1     nullptr

p2 ───→ object
```

所有权从：

```text
p1
```

转移到了：

```text
p2
```

### 2. shared_ptr

有时一个动态对象确实需要被多个地方共同使用。

例如：

```text
模块 A ──┐
         │
模块 B ──┼──→ 某个共享对象
         │
模块 C ──┘
```

这时可以使用：

```cpp
std::shared_ptr
```

例如：

```cpp
auto p1 = std::make_shared<int>(42);

auto p2 = p1;
auto p3 = p1;
```

此时三个智能指针都指向同一个对象。

`shared_ptr` 内部会维护类似：

```text
引用计数 = 3
```

当：

```cpp
p3
```

销毁：

```text
引用计数 = 2
```

当：

```cpp
p2
```

销毁：

```text
引用计数 = 1
```

最后：

```cpp
p1
```

也销毁：

```text
引用计数 = 0
```

这时动态对象才真正被释放。

因此：

\[
\boxed{
\text{最后一个 shared\_ptr 消失}
\Rightarrow
\text{资源释放}
}
\]

工程上一般遵循：

> **如果资源只需要一个所有者，优先使用 `unique_ptr`；只有确实需要共享所有权时才使用 `shared_ptr`。**

因为 `shared_ptr` 需要维护引用计数，逻辑和运行成本都更复杂。

### 3. 智能指针、自动释放与 RAII

现代 C++ 的一个重要编程习惯是：

```cpp
auto p = std::make_unique<Robot>();
```

而不是：

```cpp
Robot* p = new Robot;
```

也尽量使用：

```cpp
auto p = std::make_shared<Robot>();
```

而不是裸写：

```cpp
std::shared_ptr<Robot> p(new Robot);
```

原因并不仅仅是代码短一些，而是这种写法把：

```text
对象创建
资源所有权
自动释放
```

结合起来。

程序员不再手工追踪每一个：

```cpp
new
```

对应哪一个：

```cpp
delete
```

而是思考：

> **谁拥有这个对象？**

这实际上是现代 C++ 内存管理思想的一次重要转变：

```text
手动管理内存
      ↓
管理资源所有权
```
